# 2026-11-19: a run lost to the server's automatic updates

On cursedlogic.com/rails/, two players were in a 12-level run in room
RZTH. During level 9 their characters kept jumping back to the start
station as different characters, and the train jittered. Then the room
was gone and the run was lost. The game server had not crashed: Ubuntu's
nightly automatic updates restarted nginx 22 times and voxel-rail twice.

No fix was made. It is rare (below), so the decision was to live with
it and reconsider if it happens again in practice.

All times are UTC. The logs were collected from the server into
`~/claude/log/` on the development machine (not in git): `rail.log`
(voxel-rail's journal), `around.log` (the whole journal, 06:05 to
06:50), `apt.log` (apt history), `nginx.log` (nginx error log),
`vox-sts.txt` and `top.log`.

## What happened

| Time | Event (source) |
|---|---|
| 04:37:53 | Run RZTH starts: 12 levels, seed 688975 (`rail.log`) |
| 06:12:44 | `unattended-upgrade` starts. It installs about 100 small batches of upgrades, one after another, until after 06:51 (`apt.log`) |
| 06:13:28 | Level 9 starts (`rail.log`) |
| 06:13:47 | First of 22 nginx restarts, up to 06:48:13 (`around.log`, "Stopping nginx.service") |
| 06:15:24, 06:15:50, 06:16:33 | nginx takes 5 s to stop, then systemd kills it ("Stopping timed out") |
| 06:20:00 | The nginx package is upgraded, `1.24.0-2ubuntu7.5` to `7.19` (`apt.log`) |
| 06:21:42 | libc6 is upgraded, `2.39-0ubuntu8.5` to `8.12` (`apt.log`) |
| 06:22:01 | systemd restarts voxel-rail, together with ssh, journald, networkd and postfix. Run RZTH ends; the new server makes room VHZP (`rail.log`, `around.log`) |
| 06:30:35 | libgcc-s1 and libstdc++6 are upgraded, `14.2.0-4ubuntu2~24.04` to `~24.04.1` (`apt.log`) |
| 06:30:43 | systemd restarts voxel-rail again (`rail.log`) |

The voxel-rail process never failed:
- `NRestarts=0`;
- each stop is logged as "Stopping ... Deactivated successfully";
- memory peaked at 133 MB under a 1 GB limit;
- the kernel log has no OOM lines.

## Why

### nginx restarts

Every nginx restart closes the open WebSockets. nginx's own log records
this as "open socket #N left in connection M" followed by "aborting".
In the nginx 1.24 source, `src/os/unix/ngx_process_cycle.c` lines
951 to 969 log those lines when a worker that is shutting down exits
with connections still open.

When a connection closes, the game server removes that player
(`server/main.ts:254`). The page reconnects about a second later and
joins as a new player:
- it gets a new id, so a different character (`server/room.ts:181`);
- it is placed beside the start station (`src/sim/game.ts:618`).

The run itself carried on. While nginx took 5 s to stop, the pages got
no updates. That likely explains the jitter, but the client was not
checked.

### voxel-rail restarts

When a library package is upgraded, its file is replaced on disk. A
running process keeps the old, now deleted copy in memory until it
restarts. A tool run by the upgrade then restarts every service that
holds such a copy. That tool is most likely needrestart, but this was
not checked on the server.

The official Linux build of Node loads these libraries from the system
(`ldd` on Node v24.21.0, the same build line as the server's
`/opt/node-v24.22.3`):
- libc, libm, libdl and libpthread, all from libc6;
- libstdc++;
- libgcc_s.

So:
- the libc6 upgrade restarted voxel-rail at 06:22:01;
- the libgcc-s1 and libstdc++6 upgrade restarted it at 06:30:43.

A voxel-rail restart ends every run in progress: rooms live only in the
server's memory.

nginx was upgraded only once. Its other 21 restarts came from upgrades
of the libraries it uses (OpenSSL, libc, zlib, PCRE2 and others). The
upgrade from 7.5 to 7.19 is 14 package revisions. The newest fix is
dated 24 Oct 2026, so this was not an emergency patch. The VPS image
shipped with old packages, and this was its first full update run.

## How often to expect it

A voxel-rail restart from updates needs a new libc6, libstdc++6 or
libgcc-s1. These are Ubuntu 24.04's recent glibc security releases,
from its changelog (changelogs.ubuntu.com, glibc 2.39-0ubuntu8.12):

| Version | Date |
|---|---|
| 8.6 | 17 Sep 2025 |
| 8.7 | 30 Jan 2026 |
| 8.8 | 23 Jul 2026 |
| 8.9 | 3 Sep 2026 |
| 8.12 | 5 Nov 2026 |

That is one every 2 to 4 months recently. gcc-14's runtime libraries
changed once in the 24.04 series (19 Dec 2025, from the regular
updates channel, not the security one).

Updates install during the nightly run only. It starts at 06:00 with a
random delay of up to an hour (Ubuntu's default, from memory). This
run started at 06:12.

A night after the backlog should hold a few upgrades, not about 100.
nginx will still restart whenever OpenSSL, libc or nginx itself
changes, so the brief character resets can recur more often than the
lost runs.

## Ways to avoid it (none applied)

Least work first.

1. **Keep needrestart from restarting voxel-rail.** Then restart it by
   hand when no run is going; until then it keeps the old libc in
   memory. In `/etc/needrestart/conf.d/voxel-rail.conf`:
   ```perl
   $nrconf{override_rc}{qr(^voxel-rail\.service$)} = 0;
   ```
   The syntax is from memory and not tried on the server.
   `sudo needrestart -r l` lists pending restarts without doing them.
2. **Run the nightly updates at an hour nobody plays.**
   `sudo systemctl edit apt-daily-upgrade.timer`, then add, for example:
   ```ini
   [Timer]
   OnCalendar=
   OnCalendar=*-*-* 10:00
   RandomizedDelaySec=0
   ```
   This keeps restarts out of play time but does not stop them.
3. **Keep a dropped player for about 30 s** and let the reconnecting page
   reclaim them with a token. Players then keep their character and
   place through an nginx restart. This is game code, not yet written.
4. **Save the rooms' state when the server stops and load it back on
   start.** This is the only fix that also covers crashes and deploys.
   It needs the most game code.

Fix 1 alone stops the lost runs. Fix 3 alone stops the character resets
from nginx restarts.

## Not verified

- That needrestart issued the restarts. The journal shows only that the
  upgrade job (`apt-daily-upgrade.service`) requested them.
  `ls /etc/apt/apt.conf.d/ | grep -i needrestart` on the server would
  show it.
- The needrestart override syntax in fix 1.
- That the jitter came from the stalled connections.
- `ldd` on the server's own Node binary.
- Whether the server's unattended-upgrades setup takes the regular
  updates channel as well as the security one.
- Ubuntu's severity ratings for the nginx security fixes in 7.6 to 7.19.
